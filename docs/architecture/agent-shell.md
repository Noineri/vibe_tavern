# Agent Shell

> One chat/review/skills/profiles machine for every authoring agent, with three consumers today: the mini-app assistant, the script assistant and the sidechat. The backend holds one registry of agent kinds; the web app holds one registry of their editor hosts. A new kind plus its host plugs in from this page alone.

---

## What it is

An agent kind is a whole agent species (its base prompt, its tools, its skills, its context package), not a per-user profile.
Three kinds exist today: `experience` (the mini-app copilot), `script` (prompt and dice scripts) and `sidechat-ooc` (the out-of-character sidechat beside an RP chat).
Every kind declares an owner — `owner: "script" | "chat"`: `experience` and `script` threads are born from a script row, `sidechat-ooc` threads belong to a chat branch (see [Chat-owned threads](#chat-owned-threads)).
The generic core (stream loop, tool loop, history windowing, compaction digest, `ask_user`, plan section, skills, context links, metrics) serves any kind without kind-switches. The split-turn wait family generalizes `ask_user` (SC-23e): a permission tool stops the turn on its awaiting marker the same way, and an `{ toolCallId, decision: "allow" | "deny" }` answer resumes it — the mechanics live in `services/api/src/domain/agent/agent-split-turn.ts`.
The generic web shell (`apps/web/src/components/shared/agent-shell/AgentShell.tsx`) renders any kind's chat, review, profile and skill UI from its host descriptor.
Why one machine: the mini-app editor, the script editor and the sidechat (later the director) all need the same turn/review/session machinery, so it is written once and kinds only supply their species-level facts.

## Backend — the kind registry

The descriptor contract lives in `services/api/src/domain/agent/agent-kind.ts`.
A descriptor carries only species-level facts: the stable `id`, the `owner` (`"script"` or `"chat"`), the `servesScriptKinds` list, the `servesChatModes` list (the chat modes a chat-owned kind serves), `inheritsLegacyCopilotPair` (whether a kind with no settings row inherits the legacy shared copilot model pair), the `basePromptServiceKey`, the `skillRootId` label, the `toolSetSchema` plus `defaultToolSet`, the `recencyAnchorText`, and the `renderContextPackage` renderer for the kind-owned per-turn context package.
The table lives in `services/api/src/domain/agent/agent-kind-registry.ts`: `registerAgentKind` returns an unsubscribe, `getAgentKind` and the typed `getAgentKindOf` look one kind up, `resolveKindForScript` returns the first registered kind whose `servesScriptKinds` contains the script kind, `listAgentKinds` walks the registry (the bootstrap kind map), and `getChatOwnedAgentKind`, `kindServesChatMode` and `requireKindServesChatMode` are the chat-owner helpers.
Five typed errors carry machine-readable codes: `UnknownAgentKindError` (`UNKNOWN_AGENT_KIND`), `NoAgentKindForScriptKindError` (`NO_AGENT_KIND_FOR_SCRIPT_KIND`), `AgentKindNotWiredError` (`AGENT_KIND_NOT_WIRED`, naming the missing `stream` or `compaction` table), `AgentKindNotChatOwnedError` (`AGENT_KIND_NOT_CHAT_OWNED`), and `AgentKindModeNotServedError` (`AGENT_KIND_MODE_NOT_SERVED`).
The generic core beside the registry is `services/api/src/domain/agent/agent-prompt.ts`, `services/api/src/domain/agent/agent-stream.ts` (with the split-turn wait mechanics — ask answers and permission decisions — in its sibling `services/api/src/domain/agent/agent-split-turn.ts`), `services/api/src/domain/agent/agent-compaction.ts`, `services/api/src/domain/agent/agent-context.ts`, `services/api/src/domain/agent/agent-buffer-tools.ts`, and `services/api/src/domain/agent/agent-review-outcome-lines.ts`.
The `experience` kind is defined in `services/api/src/domain/agent/kinds/experience-kind.ts`, delegating species facts to `services/api/src/domain/interactive/copilot/experience-copilot-module.ts` and owning the `ExperienceAgentContext` shape.
The `script` kind is defined in `services/api/src/domain/agent/kinds/script-kind.ts`, delegating to `services/api/src/domain/agent/script-agent/script-agent-module.ts` and owning the `ScriptAgentContext` shape plus `SCRIPT_AGENT_RECENCY_ANCHOR_TEXT`.
The script kind's species machinery is the `services/api/src/domain/agent/script-agent/` family: `services/api/src/domain/agent/script-agent/script-agent-module.ts` (descriptor source, skill roots, profile seed), `services/api/src/domain/agent/script-agent/script-agent-prompt.ts` (system message plus the API-knowledge section), `services/api/src/domain/agent/script-agent/script-agent-stream.ts` (the turn entry the adapter calls), `services/api/src/domain/agent/script-agent/script-agent-tools.ts` (`write_buffer` / `edit_buffer` over the single `code` buffer, `run_script_test`, `plan` / `read_plan`, `ask_user`, `read_skill_file`), and `services/api/src/domain/agent/script-agent/script-agent-compaction.ts` (`ScriptAgentCompactionService`).
The `sidechat-ooc` kind is defined in `services/api/src/domain/agent/kinds/sidechat-ooc-kind.ts`: the first chat-owned kind (`owner: "chat"`, `servesChatModes: [CHAT_MODE.rp]`, empty `servesScriptKinds`), with the base-prompt key `sidechat_ooc_base`, the skill-root label `sidechat`, its own builtin profile seed, and the five sidechat tool toggles projected from `SIDECHAT_OOC_TOOL_KEYS`.
Kind modules self-register at module init and are reached through side-effect imports from their own prompt modules, so no route ever imports a kind map.
A thread resolves to its kind per request: a row with a stored `agent_kind` (a chat-owned thread) resolves to that kind through the registry, every other row follows the script path (thread row → script row → `resolveKindForScript`), and draft threads (`scriptId === null`) plus dangling script links resolve to the draft kind `experience`.
The resolver is `resolveThreadKind` in `services/api/src/api/adapters/experience-copilot-adapter.ts`; the chat-owned thread test is `isChatOwnedAgentThread` in `services/api/src/domain/agent/agent-thread-owner.ts`.
Stream dispatch goes through the adapter's `streamKinds` table (`getKindStream` throws `AgentKindNotWiredError` with table `"stream"` when the resolved kind has no entry), and manual compaction through the `compactionKinds` table (missing entry throws `AgentKindNotWiredError` with table `"compaction"`).
The routes in `services/api/src/api/routes/experience-copilot.ts` map all registry errors to the same HTTP 400 JSON shape (`{ error, code }`) on both the stream assert step and the compact route, so a wiring bug surfaces as a client-readable 400 with its own code rather than a 500.
The chat-owner route families share that mapping through `services/api/src/api/routes/agent-kind-error-map.ts`.

## Chat-owned threads

Thread ownership is typed: `AgentThreadOwner = { kind: "script"; scriptId } | { kind: "chat"; chatId; branchId; agentKind }` (`packages/domain/src/agent-thread.ts`), the twin union of `AgentPlanOwner`.
One thread table serves both owners: `experience_copilot_threads` (`packages/db/src/db-schema.ts`) keeps the script soft link `script_id` for script rows and adds the chat-owner triple `chat_id` + `branch_id` + `agent_kind` for chat rows — real FKs with cascade, so deleting a branch (or its chat) deletes its threads and messages.
The at-most-one-active invariant is scoped per owner: the partial unique index on `(chat_id, branch_id, agent_kind)` beside the script one, so two kinds on one branch coexist and the store archives only same-owner siblings.
A chat-owned row allocates a `seq` for every message and frozen event (`next_seq`, read-and-incremented inside each append transaction) and carries `rp_frontier_json` (`{ lastPosition, selected }`); script rows leave both NULL and keep `created_at` ordering.
Frozen context events live in `agent_thread_context_events` (`packages/db/src/db-schema.ts`): chat-state milestones (`rp_sync`, `selection_changed`, `variants_attached`, `branch_forked`) recorded beside the messages and interleaved with them by `seq` on the merged timeline (`listTimeline`).
The chat-owner store methods sit beside the script ones in `packages/db/src/stores/experience-copilot-store.ts` (`getActiveForChat`, `listSessionsForChat`, `startNewChatSession` — the kind is a required parameter), with the timeline read model in `packages/db/src/stores/agent-thread-context-events.ts`.
Every route that takes a chat id and a branch id checks the pair through `services/api/src/domain/chat/chat-branch-ownership.ts` (`requireChatBranch` / `findBranchOfChat`) — never a private copy of "this branch belongs to this chat".
The `servesChatModes` gate confines a kind to the chat modes it declares: creating a session on a chat whose mode the kind does not serve is a 400 `AGENT_KIND_MODE_NOT_SERVED`, while the list and active reads on such a chat answer `[]` / `null`.
The web reads the same fact from the bootstrap kind map (`servesChatModes` on the kind-settings wire) — never a second hard-coded mode check.
The lifecycle routes are the chat-scoped twins in `services/api/src/api/routes/agent-chat-sessions.ts`; the per-thread routes (`/api/experience-copilot/:threadId/...`) stay owner-agnostic and serve a chat-owned thread exactly like a script-owned one.

## Per-kind resources

Profiles live behind `services/api/src/api/routes/copilot-profile.ts`, where `?kind=` selects the kind (default `experience`) and an unknown kind is a 400 carrying `UNKNOWN_AGENT_KIND`.
Each kind has its own builtin seed (id `"builtin"`, read-only) plus its own tool-set contract, and the resolver in `services/api/src/domain/interactive/copilot/copilot-profile-resolver.ts` projects stored rows through the requesting kind's keys.
Skill libraries live behind `services/api/src/api/routes/copilot-skill.ts`, where `?kind=` selects the kind (default `experience`) for every catalog read and mutation.
The per-kind skill adapter table is `services/api/src/api/adapters/copilot-skill-adapter.ts`, which resolves the kind through the agent-kind registry first and refuses a registry-known but unwired kind instead of falling back to another kind's roots.
The script kind's library service is the optional `scriptSkillService` in `services/api/src/api/adapters/runtime-api-adapter.ts`, so lifecycle-only harnesses keep working while production wires the script roots.
The experience roots are the built-in `services/api/assets/experience-copilot/skills` plus the data-directory experience-copilot skills root; the script roots are the built-in `services/api/assets/agent-script/skills` plus the data-directory agent-script skills root; the sidechat roots are the built-in `services/api/assets/agent-sidechat/skills` plus the data-directory agent-sidechat skills root.
Compaction is per kind: `services/api/src/domain/interactive/copilot/experience-copilot-compaction.ts` (`ExperienceCopilotCompactionService`) for experience, `services/api/src/domain/agent/script-agent/script-agent-compaction.ts` (`ScriptAgentCompactionService`) for script, and `services/api/src/domain/sidechat/sidechat-compaction.ts` (`SidechatOocCompactionService`) for `sidechat-ooc`.
The base prompt key per kind is a service-prompt key: `copilot_base` (`services/api/assets/experience-copilot/base.md`) for experience, `script_agent_base` (`services/api/assets/agent-script/base.md`) for script, and `sidechat_ooc_base` (`services/api/assets/agent-sidechat/ooc.md`) for `sidechat-ooc`, each overridable through the global service-prompt profile.
The script kind's API-knowledge section reads the resolved `script` or `dice_script` service prompt matching the turn's script runtime — never both, never swapped — so a user who customized those keys loses nothing.

### Per-kind model and profile defaults

Per-kind model and profile defaults live in `agent_kind_settings` (`packages/db/src/db-schema.ts`, store `packages/db/src/stores/agent-kind-settings-store.ts`, routes `services/api/src/api/routes/agent-kind-settings.ts`): one row per kind holding the remembered provider profile + model, the kind's default profile (`default_profile_id`), and the kind's auto-compact default for NEW sessions (`auto_compact_default`, AP-20: NULL = on — both new-session paths copy it onto the created thread's `auto_compact`; the per-thread toggle is authoritative afterwards).
The binding is a remembered UI default, not a server override — the stream and compaction still take provider/model from each request.
The legacy `ui_settings` copilot pair survives as a read-time fallback only for the two pre-split kinds (`experience`, `script`), decided by the descriptor's `inheritsLegacyCopilotPair` — the one source of the fact; every later kind reads nulls without a row, so its host's `defaultModelBinding` is actually consulted.
The chat-scoped twin is `chat_agent_settings` (`packages/db/src/db-schema.ts`, store `packages/db/src/stores/chat-agent-settings-store.ts`, routes `services/api/src/api/routes/agent-chat-settings.ts`): one row per (chat, kind) holding the chat's own profile choice, with the sentinel `"builtin"` pinning the kind's built-in profile for that chat.
The stream's chat-owned profile resolution lives in one place, `CopilotProfileResolver.resolveForChat` (`services/api/src/domain/interactive/copilot/copilot-profile-resolver.ts`): chat row → kind default → built-in, with a dangling id falling through, never erroring.

### Branch plans

The agent plan's owner is a union: `AgentPlanOwner = { kind: "script"; scriptId } | { kind: "chatBranch"; chatId; branchId }` (`packages/domain/src/agent-plan.ts`).
The script-owned `agent_plans` table is untouched; `agent_branch_plans` (`packages/db/src/db-schema.ts`) holds one plan per (chat, branch) — both columns hard FKs with cascade, unique per pair.
The plan store serves both owners, and the routes are twins: `services/api/src/api/routes/agent-plan.ts` (script, unchanged) and `services/api/src/api/routes/agent-branch-plan.ts` (`GET`/`PUT /api/agent/chats/:chatId/branches/:branchId/plan`, answering the empty plan when none is stored yet).
The shared plan tools (`services/api/src/domain/agent-plan/agent-plan-tools.ts`) take the owner plus an optional read-only mode: `{ readOnly: true }` serves only `read_plan`, which is how `sidechat-ooc` reads its branch plan — plan writing is reserved for the future director kind.

### Kind meter segments

A kind's metrics may carry `segments: Array<{ key; tokens }>`; the shell's meter renders them with the host's labels when present, and the fixed system/digest/history meter otherwise.
The sidechat's five keys are `SIDECHAT_OOC_METER_SEGMENT_KEYS` (`services/api/src/domain/sidechat/sidechat-context.ts`: `context`, `rp_summaries`, `rp_messages`, `digest`, `discussion`), classified at the loader and summed at the assembly's single accounting point.

## The proposal union

The shared shapes live in `packages/api-contracts/src/agent-proposal.ts`.
A buffer proposal carries `hasProposal`, the last `proposedRules` / `proposedVisual` texts, and per-tool `summaries` in call order; it carries no `kind` field, since the field set alone identifies it.
A record proposal carries `kind: "record"` plus `id`, `recordType`, `op` (`create` / `update` / `delete`), an optional `targetId`, an opaque `payload: unknown`, and a `status` (`pending` / `applied` / `rejected`).
`AgentProposal` is the union of the two, and `isRecordProposal` narrows it structurally on the `"record"` literal.
Hosts review buffer proposals hunk by hunk in the editor pane and record proposals as cards rendered in place (outside the tool accordion, the `ask` card precedent) through the host's `recordProposalRenderers[recordType]`; the shell ships `apps/web/src/components/shared/agent-shell/RecordProposalFallbackCard.tsx` for record types with no dedicated renderer yet.
The first resolvable record type is the sidechat's `objective` proposal (`propose_objective`): apply/reject go through `POST /api/agent/threads/:threadId/proposals/:toolCallId/{apply,reject}` (`services/api/src/api/routes/agent-thread-proposals.ts`), resolved by `services/api/src/domain/sidechat/sidechat-objective-proposal.ts` — only a pending proposal resolves, apply reads the tracker at Accept time, and the status is written back into the tool row.

## The sidechat — `sidechat-ooc`

The sidechat is an out-of-character discussion beside an RP chat: the user discusses plot, characters and swipes with an assistant that sees the story chronologically and never writes into the roleplay.
It is branch-scoped (a sidechat belongs to one chat + branch; switching the RP branch switches sidechats) and one-way: RP state is read in, and nothing reaches the RP except explicit user clicks — copy into the RP composer or Accept on an objective proposal.

### The frozen timeline

The branch is read exactly as the RP model sees it: `readBranchAsModelSees` in `services/api/src/domain/sidechat/rp-branch-view.ts` reuses the send path's own derivations (`buildPipelineContext` inputs plus prompt-pipeline's `packages/prompt-pipeline/src/history-message-transform.ts` per-message transform) — macros resolved, prompt-placement regex applied, dice and mini-app report blocks in the RP prompt's wording, never the raw stored text.
The sync diff (`computeRpSync` in `services/api/src/domain/sidechat/rp-sync.ts`) detects new messages by id — positions are reused after deletes, so a position frontier would miss messages — and emits `rp_sync` batches plus `rp_selection_changed` events; `syncBeforeUserMessage` applies it in one transaction before each user message.
What is frozen never changes: later RP edits, swipes and deletions do not rewrite old events; a later selection change arrives as its own event before the next turn.
Attached variants (the "discuss in sidechat" flow) are frozen by `services/api/src/domain/sidechat/sidechat-variant-attach.ts`: one `variants_attached` event per attached message, texts through the same reader (its named-variant arm), `selected` read from the RP's own state at freeze time, and a foreign pair is the typed 400 `attached_variant_not_in_branch` with nothing frozen.

### The XML format

`services/api/src/domain/sidechat/sidechat-xml.ts` renders the owner-settled tag grammar: `<character>`, `<persona>`, `<active_lore>` with `<lore_entry>` rows, `<objectives>`, `<current_scene>`, and the timeline tags `<rp_sync>` with `<rp_message model preset>` (provenance attributes omitted at `null` — user rows carry none), `<rp_selection_changed>`, `<rp_variants>` with `<variant number model preset>`, `<rp_branch_forked at="n"/>`, and `<rp_summary>`; while a prompt preset is pinned, the package also carries an `<rp_prompt preset="…">` section — its `<block>` entries show that prompt's text verbatim with role (and `depth` on in-chat injects) and each `<known …/>` placeholder stands in for context the sidechat already holds, so the section reads as the difference worth discussing.
The loader `services/api/src/domain/sidechat/sidechat-context.ts` builds the package from the RP model's own sources: card and persona with macros resolved, active lore read from the branch's latest prompt trace (the text the RP model received), objectives from the chat row, and the scene of the thread's own branch (never the chat-level cache). While a `prompt_preset` context link is pinned, EVERY turn re-assembles the chat + branch dry (`assembleForChat({ presetId, dryRun: true })` — lore timers and script state never advance) and renders it through the pure view `services/api/src/domain/sidechat/rp-prompt-view.ts` against the sidechat's held set into the `<rp_prompt>` section; a deleted preset is a dangling link skipped like any other, and with nothing pinned the package is byte-identical.
The system message carries the static package only; each frozen event rides the message flow as its own user-role message placed by the merged timeline, so the discussion reaches the model exactly once.
The base prompt is the service prompt `sidechat_ooc_base` (`services/api/assets/agent-sidechat/ooc.md`), user-overridable like the other kinds' bases; it teaches the model the tag semantics — canonical `rp_sync` blocks, alternatives that did not happen unless selected, summaries that are not verbatim.
The events are also readable over HTTP: `GET /api/agent/threads/:threadId/events` (logic in `services/api/src/domain/sidechat/sidechat-events.ts`, routes in `services/api/src/api/routes/agent-thread-events.ts`) returns them with a `beforeMessageId` anchor each, so the web interleaves separators without a `seq` on the message wire.
The kind's six toggleable tools are `search_context` and `read_context_item` (a per-turn search session built from the turn's own branch view — `services/api/src/domain/agent/kinds/sidechat/sidechat-search-tools.ts`, the Co-Author's shape and result limit), `propose_objective` (`services/api/src/domain/agent/kinds/sidechat/sidechat-objective-tools.ts`), `todo` plus read-only `read_plan` (`services/api/src/domain/agent/kinds/sidechat/sidechat-checklist-tools.ts`), and the permission-gated `read_message_prompt` (`services/api/src/domain/agent/kinds/sidechat/sidechat-prompt-read-tools.ts`, SC-23e): `{ position, variant? }` finds the reply's swipe (the variant number from `<variant number>`, absent = the selected one), stops the turn on an `awaiting_permission` marker carrying the reply's first line, the variant number and the token estimate, and on `allow` renders the swipe's own prompt trace through `rp-prompt-view.ts` — a swipe with no linked trace (pre-SC-23b) answers that its exact prompt is unknown, never a guess.

### Three-layer compaction

`SidechatOocCompactionService` (`services/api/src/domain/sidechat/sidechat-compaction.ts`) layers the long story: (1) the RP layer reuses the RP chat's own branch summaries, read live every turn through `services/api/src/domain/sidechat/rp-summary-coverage.ts` (coverage through `buildChatSummaryContext` — the RP's own range conversion; no `rp_summary` event is ever stored); (2) the sidechat's own discussion gets a digest under the editable service prompt `sidechat_ooc_digest` (`services/api/assets/agent-sidechat/ooc-digest.md`) that keeps discussed and decided apart and never restates RP facts; (3) the recent tail stays verbatim.
The digest boundary never splits a user message from its reply, and the summarizer transcript carries the span's frozen RP events as reference rows — without them a discussion about a swipe summarizes to nothing.
Auto-compaction measures the discussion (digest + OOC rows) against the budget room left after the static context and the RP layer, reusing the shell's 80 % threshold; the whole-budget rule would fire after every exchange once the RP layer fills the budget.
Over budget, the shell's existing chronological trim drops the oldest merged-flow entries first, RP and discussion alike.

### Reverse actions

`propose_objective` returns a pending `objective` record proposal; Accept reads the tracker's on/off and mode at Accept time and reuses the insights services verbatim, while the typed 409s `objective_tracker_disabled` and `objective_proposal_already_resolved` guard a disabled tracker and a double click.
Copy into the RP composer is a web-side action only: the message action appends the reply's text to the chat draft and sends nothing.

### The fork copy

`POST /api/agent/chats/:chatId/branches/:branchId/fork-sidechat` copies the source branch's ACTIVE chat-owned threads (messages, events, context links, todo; metrics reset) and the branch plan onto the target branch: `services/api/src/domain/sidechat/branch-sidechat-fork.ts` on top of `packages/db/src/stores/experience-copilot-fork-copy.ts` (one transaction).
The fork point comes from the target branch row — `parent_branch_id` must name the source (else the typed 400 `target_branch_not_child_of_source`) — and the copy re-keys every id reference by (position, variantIndex) onto the fork's new message ids, so the copy's first sync appends nothing for the copied history; frozen text is never touched.
An occupied target (an active same-kind thread on it) is refused with the typed 400 `target_branch_thread_active` before anything is copied.
The copy ends with a `branch_forked { at }` event, rendered by the web as the separator marking where the new branch's story begins.
`GET /api/agent/chats/:chatId/branches/:branchId/sidechat-summary` answers `{ hasSessions, count }` for the fork and delete confirms.

## Frontend — the host registry and the shell

The host registry is `apps/web/src/lib/agent-host-registry.ts`, the frontend counterpart of the backend kind registry.
A host descriptor carries the stable `kind`, the i18n key table (`title`, optional `subtitle`, `placeholder`, `loading`, `emptyTitle`, optional `emptySub`, optional `mobileBackLabelKey`), the profile-modal `toolKeys`, the `profileAssignment` target (`script` or `chat`), the `bufferSpecs`, the `transport` seam, the optional `renderEditorPane` (absent means a chat-only host), `buildSendOptions`, the optional `onSendSettled` and `composerTopSlot`, the optional `toolCaption` (with interpolation params; `detail` stays the error line), the optional `defaultModelBinding` (the kind's model default when no saved binding exists), the optional `planOwner` (absent = no plan block), the optional `meterSegmentLabels` (labels for kind-provided meter segments), the optional `messageActions` (under assistant bubbles), the optional `toolbarSlot` and `mobileEditTabHeader`, and the `recordProposalRenderers` map.
`registerAgentHost` returns an unsubscribe and `getAgentHost` throws `UnknownAgentHostError` for an unregistered kind; host modules self-register at module init and their editors import them for that side effect.
`AgentKind` is a plain string, and `agentThreadKey(kind, threadId)` is the single per-thread store-key derivation: bare `threadId` for `experience` (so pre-existing localStorage drafts keep working) and `${kind}:${threadId}` for later kinds, while server-side keys stay bare.
`AgentSendOptions` (owned by the registry) carries the live buffers and step: `rules` / `visual` / `code`, `scriptKind`, `codeSaved` / `rulesSaved` / `visualSaved`, `step`, `testFeedback`, `launchContext`, `reviewSnapshot`, and `attachedVariants` (the sidechat's pending RP-variant attachments, cleared by the host on a successful send).
`AgentHostContext` hands the host its `ownerId`, `scriptId`, live `threadId`, `isSending` flag, opaque `hostProps`, and the mutable `bridge`; the editor pane assigns `bridge.session` (`onBeforeSend` plus `buildSendOptions`) every render and host surfaces prefill the chat input through `bridge.setInputPrefill`.
The transport seam (`sendStream`, `answerAsk`, `getActiveThread`, `listMessages`, `startSession`, `listSessions`, `activateSession`, `renameSession`, `setContextLinks`, optional `listEvents`) mirrors the experience client, with the lifecycle members owner-typed (`AgentThreadOwner`) so a chat host's sessions come from the chat routes; the generic shell and controller never import a kind-specific client.
The shell is `apps/web/src/components/shared/agent-shell/`: `apps/web/src/components/shared/agent-shell/AgentShell.tsx` (desktop 2-pane and mobile `[Chat][Edit]` tabs, both panes mounted), `apps/web/src/components/shared/agent-shell/use-agent-controller.ts` (send/answer/cancel through the host's transport, keyed by kind), the chat pieces (`AgentChatHeader`, `AgentMessageList`, `AgentMessageBlock`, `AgentInputArea`, `AgentMobileInputArea`, `AgentAskCard`, `AgentPermissionCard` — the ask card's clone for `read_message_prompt` decisions, fork #1 of it —, `AgentActivityCard`, `AgentToolAccordion`, `AgentContextPills`, `AgentContextMeter`, `AgentSessionSwitcher`, `AgentPlanSection`, `AgentTodoSection`, `use-agent-mention`), `apps/web/src/components/shared/agent-shell/AgentBufferReviewEditor.tsx` (hunk review over the host's buffers), `apps/web/src/components/shared/agent-shell/AgentProfileModal.tsx` (kind-filtered list, toggles read from the host descriptor's `toolKeys`), and `apps/web/src/components/shared/agent-shell/AgentSkillModal.tsx` (one kind's library at a time).
Client state is keyed by kind: `apps/web/src/stores/agent-turn-store.ts` and `apps/web/src/stores/agent-review-store.ts` take `kind` first and key their maps through `agentThreadKey`.
The two script hosts are `apps/web/src/components/build/editors/copilot/experience-agent-host.tsx` (buffers `rules` / `visual`, tool keys `COPILOT_TOOL_KEYS`, empty subtitle `agent_subtitle`, preview/code/try editor pane) and `apps/web/src/components/build/editors/script-agent-host.tsx` (single `code` buffer with hunk review, tool keys `SCRIPT_AGENT_TOOL_KEYS`, empty subtitle `agent_script_subtitle`, the script editing surface as its editor pane).
The third host is `apps/web/src/components/chat/sidechat/sidechat-host.tsx` (`sidechat-ooc`, the first chat-owned host): the owner comes from the active chat + branch, the transport is the experience client's thread-keyed members composed with the owner-keyed members of `apps/web/src/api/agent-chat-api.ts`, the plan owner is the chat branch, the profile assignment is chat-targeted, and `defaultModelBinding` offers the RP chat's active provider + model until the kind saves its own.
A chat-only host renders no editor pane; the sidechat lives in the RP chat surface — the desktop right panel (`apps/web/src/components/chat/sidechat/SidechatPanel.tsx`), the mobile `[Chat][Sidechat]` tabs (`apps/web/src/components/play/PlayMode.tsx`), one shared per-chat open flag (`apps/web/src/stores/sidechat-open-store.ts`), and the copy-to-RP-input message action on assistant replies.
The served-modes gate reaches the web through one selector, `selectSidechatServedChatModes` in `apps/web/src/api/agent-kind-served-modes.ts` (the bootstrap kind map's `servesChatModes` fact) — the panel, the tabs and the message entries all read it, never a hard-coded mode check.
The frozen events render as expandable separators (`apps/web/src/components/shared/agent-shell/AgentTimelineSeparator.tsx`), the objective proposal as `apps/web/src/components/chat/sidechat/ObjectiveProposalCard.tsx` (fork #1 of the fallback card), and the attached-variant chips sit in the composer (`apps/web/src/components/chat/sidechat/SidechatVariantChips.tsx`).

**Composer attachments (all hosts):** `use-agent-composer-attachments.ts` wraps the shared draft hook (`hooks/use-attachment-draft.ts`, `allowedKinds: ["image", "file"]` — see [Frontend](./frontend.md#attachments-composer--message-chips)); both composer mounts (`AgentInputArea`, `AgentMobileInputArea`) attach. Sends go out as `onSend(content, attachments)`; the optimistic bubble carries them, edit-last keeps the user row's attachments (regenerate body unchanged), and deleting a turn deletes its now-unreferenced asset files unless the host passes `keepAttachmentFiles`. Sent files render through `agent-file-attachment.tsx` with the same action menu as the RP chat (summarize / clear / include / delete over the per-thread attachment routes), and images get the RP lightbox actions (`agent-lightbox-actions.tsx`). After a settled turn the host's `AgentShell.handleTurnSettled` refreshes the thread (`refreshThread`) so actioned chips reflect persisted state.

## Adding a kind + host — the checklist

1. Add the backend descriptor in `services/api/src/domain/agent/kinds/` (one per-kind file beside the three kinds there): `id`, `owner`, `servesScriptKinds` / `servesChatModes` (whichever the owner needs), `inheritsLegacyCopilotPair` (`true` only for kinds that predate per-kind model settings), `basePromptServiceKey`, `skillRootId`, the tool-set schema plus default set, `recencyAnchorText`, and the kind-owned `renderContextPackage` input shape.
2. Self-register the kind at module init and reach it through a side-effect import from its prompt module, mirroring the kind side-effect import in `services/api/src/domain/agent/script-agent/script-agent-prompt.ts`.
3. Add the adapter entries in `services/api/src/api/adapters/experience-copilot-adapter.ts`: one `streamKinds` entry and one `compactionKinds` entry; a registered kind missing either throws `AgentKindNotWiredError` (HTTP 400 with code `AGENT_KIND_NOT_WIRED`) instead of streaming.
4. Add the skill roots (built-in asset directory plus data-directory root, mirroring `services/api/assets/agent-script/skills`) and wire the library service beside `scriptSkillService` in `services/api/src/api/adapters/runtime-api-adapter.ts` plus the per-kind table in `services/api/src/api/adapters/copilot-skill-adapter.ts`.
5. Add the profile seed (builtin `script`-style seed) and extend the per-kind projection in `services/api/src/domain/interactive/copilot/copilot-profile-resolver.ts`, so `?kind=` lists and validates only the new kind's tool keys.
6. Add the service-prompt base key in `services/api/src/domain/service-prompts/service-prompt-registry.ts` with its asset base file beside the other kind bases, and point the kind's `basePromptServiceKey` at it; if the kind needs API knowledge, read the matching existing service-prompt keys rather than copying their text.
7. Add the host descriptor in a new per-kind host module beside the three hosts: `kind`, the i18n keys, `toolKeys` (the wire-contract key list), `bufferSpecs`, the `transport` delegation, and `recordProposalRenderers` (empty until the first record renderer arrives); the optional members (`profileAssignment`, `defaultModelBinding`, `planOwner`, `meterSegmentLabels`, `messageActions`, `composerTopSlot`, `onSendSettled`) exist for the kinds that need them.
8. Add the editor pane behind `renderEditorPane` (or omit it for a chat-only host), assigning `bridge.session` with `onBeforeSend` and `buildSendOptions`; the script host's pane pattern is the reference for a single-buffer editor.
9. Add the i18n keys in `apps/web/src/i18n/locales/en.json` and `apps/web/src/i18n/locales/ru.json`, then run `bun run i18n:types`; the shell resolves descriptor keys only, so a typo is a compile error.
A chat-owned kind additionally serves a mode list (`servesChatModes`), so its sessions can be refused on chats it does not serve, and its threads come from the chat-owner store methods — the sidechat (`services/api/src/domain/agent/kinds/sidechat-ooc-kind.ts` + `apps/web/src/components/chat/sidechat/sidechat-host.tsx`) is the reference pair.
